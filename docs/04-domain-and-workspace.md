# Domain Model and Workspace Format

## Purpose

This document defines the concepts the application must preserve and a proposed portable workspace layout. It is a design contract, not yet a final serialisation specification.

## Domain concepts

### Workspace

A user-controlled root directory containing imported source assets, generated artefacts, human knowledge, exports and an internal catalogue.

A workspace has:

- a stable identifier;
- a display name;
- a format version;
- creation and last-opened metadata;
- application compatibility information;
- optional source-system profiles without secrets.

### Import operation

One attempt to ingest a source asset or source system.

It records:

- operation identifier;
- source type;
- start and completion time;
- result status;
- parser and extractor versions;
- warnings and errors;
- created or reused revisions.

### Source asset

An externally supplied item such as an RDL file, SQL script or database-object definition.

The application preserves original bytes and basic metadata. A source asset can have multiple revisions.

### Revision

An immutable version of a source asset identified by content hash and import context.

A revision is not overwritten when a later source changes. Reprocessing with a newer parser creates new generated artefacts associated with the same source revision rather than falsifying the original import date.

### Report

A logical SSRS report that can have multiple imported revisions.

### Dataset

A named report dataset belonging to a report revision. It can contain embedded command text, call a stored procedure or reference a shared dataset.

### Database object

A table, view, procedure, function, synonym, trigger or other imported SQL Server object with one or more revisions.

### Signature

A deterministic structured representation derived from source SQL or report logic. It is versioned and reproducible from the preserved source where supported.

### Reference

A claimed relationship such as a dataset referencing a table or a procedure calling a function.

Reference status may be:

- unresolved;
- uniquely resolved;
- ambiguously resolved;
- externally referenced;
- dynamically constructed;
- invalid against the imported schema.

### Finding

An evidence-backed result produced by a rule, comparison or conformance evaluation.

A finding contains:

- rule identifier and version;
- severity and confidence;
- evidence references;
- affected entities;
- lifecycle status;
- human disposition where reviewed.

### Review question

A focused request for information that cannot be safely inferred. Questions should be structured enough to support reuse and comparison.

### Decision

A human-confirmed answer with scope, provenance, author and timestamp. Decisions are immutable; superseding decisions point to earlier records.

### Metric contract

An approved definition of a business statistic, including its grain, date semantics, required sources, required rules, permitted variations, prohibited patterns and reference implementations.

### Suggestion

An AI- or heuristic-generated proposal. Suggestions are never silently promoted to decisions.

## Evidence classification

Every important record should identify one of the following origins:

- `SourceFact` — directly extracted from source content or database metadata;
- `DeterministicInference` — produced by a named parser or rule;
- `HumanDecision` — explicitly confirmed by an authorised user;
- `AiSuggestion` — generated by a model and awaiting review.

|
|-- workspace.json
|-- catalog.db
|
|-- source/
|   |-- rdl/
|   |   `-- <report-id>/<revision-id>/original.rdl

|   |   |-- summary.md

|   |   `-- datasets/<dataset-id>/

|   |       `-- fields.json
|   |

The exact path names may evolve before implementation. Once a released workspace format exists, changes require migration and compatibility testing.

## Workspace manifest

Illustrative fields:

```json
{
  "workspaceFormatVersion": "0.1",
  "workspaceId": "ws_01J...",
  "name": "JFK Law Reporting Intelligence",
  "createdAtUtc": "2026-07-30T00:00:00Z",
  "createdByApplicationVersion": "0.1.0-dev",
  "catalogue": {
    "provider": "sqlite",
    "relativePath": "catalog.db"
  },
  "settings": {
    "preserveSourceTimestamps": true,
    "defaultSqlDialect": "SqlServer2022"
  }
}
```

Do not store passwords, tokens or reusable database credentials in this file.

## Revision layout

A revision directory should be immutable after successful publication except for explicitly append-only diagnostic metadata. Reprocessing should create a new generated-analysis version or replace only a known derived cache after preserving prior evidence according to the adopted retention policy.

## File naming

- Use stable IDs in paths to avoid unsafe and conflicting names.
- Preserve user-facing source names in metadata.
- Generate a sanitised display slug only for convenience.
- Never infer identity from a file path alone.
- Use UTF-8 for generated text artefacts.
- Preserve original bytes for source files even when encoding is unusual.

## Catalogue responsibilities

The catalogue should index and relate artefacts, not hide them. Suggested early tables include:

- WorkspaceInfo;
- ImportOperation;
- SourceAsset;
- SourceRevision;
- Report;
- ReportRevision;
- Dataset;
- GeneratedArtefact;
- ParserDiagnostic;
- DatabaseSource;
- DatabaseObject;
- DatabaseObjectRevision;
- ObjectReference;
- ReviewQuestion;
- HumanDecision;
- Finding;
- SchemaMigration.

Do not prematurely create tables for every future concept. Introduce persistence with each vertical slice.

## Idempotence rules

### Identical RDL import

When the source hash and relevant import identity match an existing revision:

- do not create a duplicate source revision;
- permit reprocessing only when requested or required by parser-version changes;
- report that existing content was reused.

### Changed RDL import

When the logical report appears to match but the source hash differs:

- create a new immutable revision;
- preserve the previous revision;
- avoid asserting logical identity when matching is uncertain;
- allow the user to confirm or correct report identity.

## Source locations

Generated facts and diagnostics should reference source locations when practical:

- RDL XPath or stable element path;
- source line and column if available;
- SQL fragment offset and length;
- database object and definition revision;
- report, dataset and expression identity.

## Human knowledge files

Human decisions and metric contracts should remain serialisable to readable files, even when the catalogue provides the primary editing transaction.

Benefits:

- source control and review;
- portability;
- transparent diff history;
- model-independent retrieval;
- disaster recovery if the catalogue must be rebuilt.

## Rebuildability objective

A future workspace-rebuild command should be able to recreate most catalogue state from preserved source and knowledge artefacts. Operational metadata such as UI history may be excluded, but business knowledge and provenance must not depend solely on SQLite.
